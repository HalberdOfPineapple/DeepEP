E6 · Skew injection: who waits for whom

Delay one rank by a known amount before dispatch and check that the cross-rank stamps give the delay back, and that host stamps tell a busy GPU from a slow host.

experiment E6 · 8 cases · 4 × H100 on host GPUs 4–7 · scripts: e6_sweep.py, common/run_dispatch.py (--skew-*), e6_analyze.py · generated 2026-10-13 17:18

1. Motivation

A dispatch cannot start moving data until every rank has arrived at its opening barrier, and cannot finish until every rank has arrived at its closing barrier. So if one rank reaches the kernel late, because the GEMM before it ran longer, because its launch was delayed, or because its previous communication kernel had not finished, every other rank sits in the barrier for exactly that long, with the fabric idle. From inside any single rank this looks like "the barrier took long"; nothing on that rank says which peer was late or why. The suspicion is that in a real pipeline this idle time is a large share of the communication phase and is routinely misread as communication cost.

Two things are tested. First, whether the per-rank stamps already in the traced kernel, placed on one clock with the per-run calibration, attribute an opening-barrier wait to the rank that caused it and recover the amount of delay. Second, whether host-side timestamps around the launch can tell a delay that happened on the GPU before the kernel (a long preceding kernel) from one that happened on the host before the launch (a slow CPU). Those two have the same signature inside the kernel and different fixes.

2. Methodology

In one sentence: delay rank 0 by a known amount right before each dispatch, stamp the kernel entry and both barriers on all four ranks, align the stamps on one clock, and check that the other ranks' barrier waits equal the injected delay.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. The baseline instrumented build is used throughout. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 5 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: the delay injected on rank 0 before each traced dispatch, 0, 20, 100, 500 and 2,000 µs, as a spin kernel on rank 0's stream (the GPU is busy, the host is not); one case injects 100 µs as a host busy-wait instead (the launch is late); and two cases at 256 tokens, where the kernel is short enough for the delay to dominate. The Kineto step is skipped; all numbers come from the stamps.

2.2 How each reported number is computed

  • Opening-barrier wait of a rank = release stamp − its own arrive stamp (both on SM 0 of that rank, no clock alignment needed). For the on-time ranks this should equal the injected delay plus the barrier's base cost.
  • Entry lag = rank 0's kernel-entry stamp − rank 1's, after placing both on rank 0's clock with the mean of the two calibrations that bracket the dispatch. This should equal the injected delay in GPU mode and in host mode alike.
  • Host call → kernel entry on each rank: the host stamp taken just before buffer.dispatch(), mapped onto that rank's GPU clock through the two (host, GPU) timer samples that bracket the repeat, subtracted from the entry stamp. In GPU mode rank 0's launch queues behind the spin kernel, so this grows by the delay; in host mode the call itself is late and this stays small.
  • Data plane = last dispatch warp finished − opening-barrier release; closing wait = closing-barrier release − last warp finished; kernel span = kernel end − kernel entry. All on the on-time ranks (median over ranks 1–3 and the five repeats) unless stated.

2.3 Configuration

  • 4 ranks on host GPUs 4–7, 16 SMs, 4,096 tokens per rank (256 for the two short cases), uniform routing, CPU sync on, baseline instrumented kernel. Host processes pinned to socket-1 cores.

3. Results

The on-time ranks pay the delay, minus about 85 µs that the launch path hides, and the cross-rank stamps name the late rank. With no delay the opening barrier costs ranks 1–3 11 µs. With 100 µs injected on rank 0's GPU they wait only 18 µs; with 500 µs, 424 µs; with 2,000 µs, 1924 µs. The difference, about 85 µs, is the host-side cost of buffer.dispatch() before the kernel is enqueued (call → entry is 68 µs with nothing in the way, Figure 4): a GPU that is still busy for less than that when the host starts the call delays nothing. A host-side delay of 100 µs, by contrast, is paid almost in full (93 µs). In every case the entry lag recovered from the aligned clocks matches the wait (Figure 3 left), so the stamps say which rank was late and by how much, and rank 0's own wait stays at 4 µs. The data plane on the on-time ranks is 541 µs without and 543 µs with the largest delay: skew is idle time, not slower communication.
Host stamps separate a busy GPU from a slow host. Inside the kernel both cases are identical. 4. Conclusions

  1. Attribution of barrier time works with what the traced kernel already has. Entry, arrive and release stamps on every rank, aligned by the per-run calibration, recover the effective delay to within a few µs and point at the rank that caused it. Without the alignment, each rank only knows that it waited.
  2. About 85 µs of GPU-side slack before a dispatch is free. The host needs that long inside buffer.dispatch() before the kernel is enqueued, so a preceding kernel that overruns by less than that on one rank costs the others nothing; one that overruns by more costs them the excess, one for one. A host-side delay has no such allowance. This number is a property of the DeepEP Python/C++ launch path on this host and is itself worth watching: it is also the floor of the decode critical path (E9).
  3. Skew is pure idle. Nothing about the data plane changes; the delay beyond the launch allowance reappears as fabric idle time on the other ranks, and in the 256-token case it is most of the kernel (30 µs waited of a 75 µs span with 100 µs injected). Any tool that reports the communication phase by kernel duration counts this idle time as communication.
  4. A host stamp per launch is cheap and necessary. It is the only signal that distinguishes a GPU-side cause (a long preceding kernel, which is the compute-skew case) from a host-side one (launch latency, CPU contention); the kernel-internal view cannot.
  5. Resolution. The host-to-GPU clock mapping used here is good to about ±5 µs; the GPU-to-GPU alignment to about 0.1 µs. For decode-size kernels the host side is the coarse one.
Limits. One delayed rank; four ranks; the delay is injected at a clean point (before the launch), whereas a real pipeline's skew comes from a preceding kernel whose own end stamp would be the natural anchor. Host-side mapping costs 50 tiny launches per repeat and is not something to leave on per kernel in decode.
