E9 · The decode critical path

128 tokens per rank: the chain from host call to host return cut into eight segments, and how SM count, CPU sync and counter padding move each.

1. Motivation

In decode each rank dispatches a handful of tokens, so the dispatch is not a bandwidth problem but a latency chain: launch, opening barrier, the count exchange, a single token per warp, the closing barrier, the epilogue, and the host reading the counts before it can allocate the expert inputs. Nothing in this chain is large, but all of it is serialised and it repeats for every layer of every decode step. The question is what the chain is made of at 128 tokens, which segment is the longest, how much of it is on the host rather than on the GPU, how it changes with the number of SMs and with the CPU-sync option, and whether the slot-counter padding of E3 moves anything at this size. A per-kernel duration from a profiler answers none of these; the segment decomposition is what a tool must produce.

2. Methodology

In one sentence: run 100 dispatches of 128 tokens per rank per case, stamp the host call and return and map them onto the GPU clock, cut the span from host call to host return into eight segments with the in-kernel stamps, and compare cases.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. The padded case uses the --pad-counters build. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 100 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: SM count (4, 16, 32), the CPU-sync option (on: the host waits for the token counts inside dispatch(); off: dispatch() returns immediately), and the slot-counter layout (padded, as in E3). 128 tokens per rank, 100 traced repeats per case; the Kineto step runs with 50 iterations and gives the reference kernel time.

2.2 How each reported number is computed

  • Segments per (rank, repeat), in µs: host call → kernel entry; entry → opening-barrier release; release → notify phase F done (all peers' counts seen); F → H (prefix sums written, mailbox); H → last dispatch warp finished; last warp → closing-barrier release; release → kernel end; kernel end → host return. Host stamps are mapped onto the GPU clock with the bracketing timer samples; the bracket half-width (about ±5 µs) is reported.
  • Call → return is measured purely on the host (no mapping) and is the end-to-end number a caller experiences with CPU sync on.
  • Entry skew = latest − earliest kernel entry across the four ranks on one clock (per-run calibration), the launch skew the opening barrier absorbs.
  • Slot atomic latency per lane, as in E3. Kineto kernel µs as in E0 (50 iterations, L2 flush and barrier between).

2.3 Configuration

  • 4 ranks on host GPUs 4–7, 128 tokens per rank, top-8 of 256 experts, uniform routing, expert alignment 128, host processes pinned to socket-1 cores.

3. Results

The 128-token dispatch costs 142 µs from call to return at 16 SMs (p99 206 µs), of which the kernel itself is 43 µs. The host-side launch path (call → entry) is 63 µs and the return path (kernel end → return) 37 µs; inside the kernel the longest segments are the count exchange (6 µs), the data plane (13 µs) and the opening barrier (19 µs, with 18 µs of entry skew behind it).
What moves. Turning CPU sync off removes 31 µs from the caller’s view (call → return 112 µs) but not from the GPU chain, whose segments are unchanged. Going from 16 to 4 SMs makes the data plane 34 µs instead of 13 µs; 32 SMs gives 10 µs and a 17 µs opening barrier. Padded counters change the atomic from 96 to 96 ns and the end-to-end by -3 µs: nothing, as E3 predicted.

4. Conclusions

  1. The decode chain is host and synchronisation, not bytes. Launch path, two barriers and the count exchange are most of the 142 µs; the data plane at 128 tokens is 13 µs. A tool that reports kernel time (32 µs by Kineto) sees 23 % of what the caller pays.
  2. Host stamps are part of the instrument. The call → entry segment (63 µs) is as large as the biggest in-kernel segment and invisible to any GPU-side probe; E6 showed the same number as the allowance that hides a late peer.
  3. The SM count is a latency knob in decode. Fewer SMs lengthen the data plane one for one; more SMs lengthen the barriers (grid syncs over more blocks). DeepEP’s default of 20 is a bandwidth choice; a decode-specific count would be chosen from this decomposition.
  4. Tails. The p99 of the end-to-end is 206 µs against a p50 of 142 µs; the segment p99s (Figure 3) show which segment carries the tail.
Limits. One repeat of the no-CPU-sync case had a host-side stall of over a second between call and return (a host event unrelated to the kernel; it is kept in the table's p99 and cut from the CDF). Host-to-GPU mapping is good to about ±5 µs, comparable to the smallest segments. No model compute between dispatches, so the launch path runs on an idle host and GPU; in a real decode loop the previous kernel’s end is the anchor. Four ranks; the count exchange grows with rank count.
