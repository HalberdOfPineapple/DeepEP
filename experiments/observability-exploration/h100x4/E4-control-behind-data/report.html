E4 · Control-plane stores behind the data plane

How long an 8-byte notify store takes to cross to a peer while 240 warps are pushing 14 KB stores through the same ports, measured with two in-kernel timestamps and a one-time clock calibration.

experiment E4 · 8 cases · 4 × H100 on host GPUs 4–7 · scripts: e4_sweep.py, common/apply_trace_patch.py (--relocate-recv), e4_analyze.py; clock offsets from E1

1. Motivation

Dispatch has a small control plane inside its data plane: the 260 eight-byte count stores that SM 0 sends to its peers (phase E) travel the same L2, NVLink ports and switch queues as the 14 KB bulk stores of the dispatch warps, with no priority. The receiver cannot finish phase F, and the host cannot allocate the outputs, until the last of them arrives. In prefill this is hidden behind the data; in decode or under incast the control plane can become the critical path. The question is how much the data plane delays a small store, whether the delay depends on the destination address (does the address pick a path), and what it costs end to end. This is the first experiment that needs timestamps on two GPUs, so it also exercises the clock alignment from E1.

2. Methodology

In one sentence: stamp the clock on the sending GPU right after each count store is issued and on the receiving GPU the first time its poll loop sees that count, align the two clocks, and subtract.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. For the relocated cases the patch also redirects the receive-count array to an unused region of the window at a fixed byte offset, on every rank alike. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 8 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here is the load on the data plane and the address of the count array, as the cases listed in 2.3. Only step 5 matters for this experiment; the kernel-time run of step 4 is used only to report the kernel length each chain is compared against.

2.2 How each reported number is computed

  • Sender stamp SEND[i]: in the notify phase, the SM 0 thread that stores count i into a peer's memory with st.relaxed.sys reads the clock immediately after the store instruction.
  • Receiver stamp RECV[i]: the SM 0 thread on the destination rank that polls count slot i reads the clock in the first poll iteration that sees the slot's value ready. Its resolution is one poll iteration, one L2 load.
  • One-way latency = RECV[i] − SEND[i] − offset(sender → receiver), where the offset is the mean of the two clock calibrations that bracket that dispatch (step 5). The difference between the two calibrations is reported as the drift bound; within one dispatch the offsets moved by at most 0.8 µs. Half the ping-pong round trip (0.65 µs) is the reference for an unloaded store-to-visible time. Only the first slot each polling thread handles is used, 128 stores per receiver per dispatch.
  • Per-pair matrix: the same one-way latency grouped by (sender, receiver).
  • E issued → F done: SM 0's phase stamps on the receiving rank, from the moment its own count stores were issued to the moment all incoming counts had been seen. This is the end-to-end cost of the count exchange on the receiver's critical path.

2.3 Configuration and cases

  • Cases: notify with an almost empty data plane (64 tokens), light data (256 tokens, from E0), full data at 16 and 32 SMs, incast ratio 4 (from E2), and the receive array relocated by 4 MiB and by 4 MiB + 64 B into the unused hybrid signal region of the window (same offset on every rank, so the symmetric addressing still holds). 8 traced repeats per new case.
  • Clock offsets between the four GPUs are measured inside each run, immediately before and after every traced dispatch, with a 400-round ping-pong per ordered pair through torch symmetric memory (common/clocksync.py). A first attempt with offsets taken from E1 an hour earlier produced one-way values of ± milliseconds: the GPUs' %globaltimer clocks drift against each other between runs (the 0↔1 offset moved by about 8 ms over an hour), so "one calibration per session" is not good enough; "one per kernel" is, and it costs about 12 ms for four ranks.

3. Results

A count store takes 1.79 µs one way on a quiet fabric and 2.30 µs p50 / 18.4 µs p99 while 240 warps are storing data, 3.33 / 20.2 µs at 32 SMs, and 31.23 / 70.4 µs under incast. With a balanced data plane the median is barely touched but the tail grows fivefold; under incast the median itself is 17× the quiet value, and the receiver's wait for all peers' counts (E issued → F done) stretches to 33 µs. The inflation is the per-SM store FIFO of E2 seen from the control plane: SM 0's count stores queue behind its own dispatch warps' 14 KB stores to the hot rank.
Relocating the receive array does not change the latency: 2.56 / 18.2 µs for relocated +4 MiB, 2.30 / 19.5 µs for relocated +4 MiB + 64 B, 3.58 / 15.9 µs for relocated +4 MiB. At this granularity the address does not select a slower or faster path for an 8-byte store; whatever interleaving the hardware applies does not separate control from data.

4. Conclusions

  1. The control-behind-data delay is measurable and small at this scale. The control plane shares the sender's egress queue with the data plane and pays the same queueing delay; the per-pair matrix shows the inflation is uniform across destinations, consistent with E2's shared-FIFO result rather than with a congested path.
  2. End-to-end weight. E issued → F done is 14 µs with the full data plane, of a 598 µs kernel; the host learns the output sizes early enough in prefill. In the 64-token case the same chain is 4 µs of a 23 µs kernel, which is the decode regime's cost: with few tokens, the count exchange and the barriers are most of the kernel.
  3. Method, and a correction to the clock-sync assumption. Two in-kernel timestamps plus a per-run clock calibration gave one-way latencies for 128 stores per receiver per dispatch at no measurable kernel cost. The calibration cannot be done once per session: the per-GPU clocks drift by milliseconds per hour relative to each other, which is far more than FabricPerf reports for intra-node pairs; the triangle closure of a single calibration is still about 100 ns, so the offsets are precise at the instant they are taken. The receiver stamp is limited by the poll loop; a hardware arrival timestamp does not exist.
Limits. The light-data (E0) and incast (E2) traces were recorded before in-run calibration existed and are not included. Receiver-side resolution is the poll iteration; only the first slot per polling thread is used. Four ranks.
