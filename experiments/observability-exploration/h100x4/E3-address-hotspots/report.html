E3 · Address hot spots: the slot-counter line

Does serialising ~15,000 returning atomics per dispatch on one 32-byte sector cost anything, and does padding the counters change it.

experiment E3 · 8 runs · 4 × H100 on host GPUs 4–7 · scripts: e3_sweep.py, common/apply_trace_patch.py (--pad-counters), e3_analyze.py

1. Motivation

DeepEP allocates destination slots with a returning atomicAdd on scaleup_atomic_sender_count[dst], eight (here four) consecutive ints in one 128-byte line, from every dispatch warp for every (token, destination) pair: ≈ 14,800 atomics per dispatch per GPU at four ranks. All of them serialise at one L2 slice, and the returned value is on the warp's critical path, so the concern is that this one cache line becomes a funnel whose latency grows with the number of warps and destinations. E0 already reported a flat 96 ns p50, which suggests the funnel is cheap at this scale; this experiment tests that directly by giving each counter its own line, at two concurrencies and in both the prefill (4,096 tokens) and the decode-like (256 tokens) regime, and records the two NVLink barriers' arrive-to-release time on SM 0 as the other address funnel.

2. Methodology

In one sentence: time every slot-allocation atomic from issue to return, with the four counters sharing one cache line as DeepEP has them and with each counter moved to its own line, and see whether the layout changes anything.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. For the padded build the patch also changes the index stride of the slot counters where they are allocated and where they are reset. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 30 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 5 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: two kernel builds, baseline and --pad-counters (counter stride 32 ints, so each counter has its own 128-byte line), each at (16, 32) SMs × (4,096, 256) tokens. Eight runs in all; routing uniform.

2.2 How each reported number is computed

  • Atomic latency (Figure 2): the warp stamps the clock just before its lanes issue the returning atomicAdd, and each lane stamps it again when its value comes back; the difference, per lane, is one sample. Both stamps are taken by the lane that issued the atomic. Percentiles are over all lanes, warps, ranks and the five repeats. The clock's 32 ns granularity shows as steps in the CDF.
  • Iteration p50 = stores issued − loop top, per token, the same quantity E0 decomposes.
  • Opening / closing barrier µs (Figure 3): SM 0's stamp just before the gpu_barrier call and just after it returns. The opening barrier includes any launch skew between ranks; the closing barrier includes waiting for the slowest rank. Neither can be attributed to the barrier word alone with four ranks, so they are reported, not interpreted as contention.
  • Kernel µs from step 4, mean ± standard deviation over the four ranks.

2.3 Configuration

  • 4 ranks on host GPUs 4–7, top-8 of 256 experts, uniform routing, expert alignment 128, CPU sync on.

3. Results

The counter funnel costs nothing measurable at four ranks. Atomic latency is 96 ns p50 / 96 ns p99 at 16 SMs with the shared line and 96 / 96 ns padded; at 32 SMs 96 / 96 ns versus 96 / 96 ns. Kernel time changes by +0.2 % (16 SMs) and +0.2 % (32 SMs), inside run-to-run noise. The L2 atomic unit absorbs this rate (one atomic every ~40 ns per GPU on average) without queueing.

4. Conclusions

  1. The slot-counter funnel is a non-problem at this scale: with four destinations and 240 warps the returning atomics complete in about 100 ns regardless of layout. The concern scales with destinations and warps (eight ranks double the issuers per line, 72 ranks would put nine lines' worth of counters in one), so the padded layout is a free insurance rather than a fix; the measurement to repeat on eight GPUs is this one.
  2. Where the µs go instead is the barrier arrive-to-release time, which is launch skew and peer skew rather than word contention; E6 (skew injection) and E9 (decode critical path) are the experiments that decompose it, and the opening-barrier numbers here are their baseline.
  3. Method note. The per-lane atomic timing costs two timer reads per token and is the right way to watch this funnel grow with rank count; no counter in the memory system exposes per-line serialisation.
Limits. Four ranks only; the per-sender barrier-word variant was not implemented (it changes the barrier protocol on both sides). Timer granularity 32 ns.
