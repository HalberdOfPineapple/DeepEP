E5 · Compute interference: which step pays, and on which side

HBM-bound copies or compute-bound GEMMs run beside the traced dispatch on all ranks or on one; the per-step and per-destination stamps say where the time goes.

1. Motivation

DeepEP's kernels are meant to run beside the model's GEMMs, on a few SMs, so that communication overlaps compute. The compute shares three resources with the dispatch warps: HBM bandwidth (the warps read their tokens from HBM with TMA loads), the L2 (slot atomics and the path of every store out of the SM) and, on the receiving side, the memory system that absorbs incoming NVLink writes. The question is which of the dispatch's steps slows down when the GPU is also busy, by how much, and whether the slowdown happens on the sending GPU (its loads and its egress) or on the receiving GPU (its ingress), because the two have different signatures and different remedies. A tool that only sees kernel duration cannot tell "my own GPU was busy" from "my peer's GPU was busy" from "the link was busy".

2. Methodology

In one sentence: run a queue of short HBM-bound copies or compute-bound GEMMs on a second stream of the same GPU while the traced dispatch runs, on all four ranks or only on rank 0, and compare each step of the per-token loop and each (sender, destination) store latency with the undisturbed run.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. The baseline instrumented build is used throughout. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 3 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: the background kind (none, 32 MB copies, 2048³ GEMMs) and its placement (all ranks or rank 0 only), at 4,096 tokens and 16 SMs; plus the 256-token case with and without copies on all ranks. The background queue is issued on the side stream right after the clock calibration and before the barrier that precedes each traced dispatch, so it is already running when the dispatch starts and outlasts it. The Kineto step runs without background and gives the undisturbed kernel time; kernel time under load is the entry-to-end span from the stamps.

2.2 How each reported number is computed

  • Per-token loop parts on a rank, median over its tokens, warps and repeats: C1 slot wait (loop top → slot free), C2 prepare (slot free → token loaded, which contains the TMA load of the token from HBM and the slot atomic), C3 issue (token loaded → all stores issued).
  • Per-destination store latency: per lane, wait return − store issue, grouped by sender rank and destination rank. "Ranks 1–3 to rank 0" pools the three clean senders' stores into the (possibly loaded) rank 0; "ranks 1–3 to each other" is the median over the three idle destinations; "rank 0 to its peers" is the loaded sender's own stores.
  • Slot atomic latency per lane, as in E3. Kernel span = kernel end − kernel entry on SM 0, per rank, median over repeats.
  • Background intensity: the duration of one background kernel alone, measured with CUDA events before the repeats (32 MB copy ≈ HBM rate; one GEMM ≈ tensor-core rate).

2.3 Configuration

  • 4 ranks on host GPUs 4–7, 16 SMs, uniform routing, top-8 of 256 experts, CPU sync on, L2 flush off, 120 background kernels per repeat (30 in the 256-token case).

3. Results

Where the slowdown lands. With HBM copies on all ranks the kernel span on rank 0 goes from 610 to 793 µs; with GEMMs on all ranks to 656 µs. In the loop, C2 prepare (the HBM load of the token) is ×1.64 under copies and ×1.07 under GEMMs; C1 slot wait ×1.34 and ×1.04; C3 issue ×1.29 and ×1.04.
Sender side or receiver side. When only rank 0 is loaded with copies, the clean senders' stores into rank 0 take 4.8 µs p50 against 4.8 µs to each other (undisturbed: 4.9 µs), while rank 0's own stores to its peers take 6.3 µs (undisturbed 4.8 µs). The same split for GEMMs on rank 0: into rank 0 4.9 µs, between the others 4.9 µs, from rank 0 5.0 µs. Because the per-SM store queue is shared across destinations (E2), a receiver-side slowdown on one destination spreads to the clean senders' other destinations too; the destination split in Figure 3 shows how much of it is destination-specific.
The largest effect is not in the data plane but in the launch. When only rank 0 runs the background, ranks 1–3 wait 906 µs (copies) and 1736 µs (GEMMs) in the opening barrier, against 5 µs undisturbed: rank 0's cooperative dispatch launch could not get its 16 SMs while the background queue kept the GPU full, and every other rank idled for that long. In the "all ranks" cases the same delay happens on every rank at once and is invisible in the barrier wait; it appears only as a later kernel entry relative to the host call, which E6 and E9 measure. For a kernel meant to run beside GEMMs this launch wait is the first number to watch, and no in-kernel stamp sees it.

4. Conclusions

  1. Compute interference is measurable per step and per side with the stamps already in place. The loop decomposition shows which step pays (the HBM load in C2 under memory-bound neighbours, the store path in C1/C3 when the egress or the peer's ingress is slower), and the per-destination split on clean senders isolates the receiver-side component. These are the signatures a tool needs to attribute "communication got slower" to the co-running compute rather than to the fabric.
  2. The per-SM shared store queue blurs destinations. A loaded receiver slows the clean senders' stores to it, and through the shared queue their stores to everyone else; the destination mix of what is queued is needed to attribute the delay to the loaded peer, as in E2.
  3. Launch scheduling dominates when the GPU is full. Even with 30 µs background kernels the cooperative launch of dispatch waits 1–2 ms behind them; with a single 8 ms GEMM (a first attempt) it waited the whole GEMM. This is a sync-in (phase A) effect, invisible inside the kernel, and in a pipelined MoE it is what "overlap" would cost first.
Limits. Synthetic background kernels, not real MoE GEMMs; no PM-sampled HBM/L2 counters alongside (CUPTI PM sampling was not set up), so the background intensity is characterised only by its standalone kernel time. Four ranks. The 256-token case has few tokens per warp and is noisy.
