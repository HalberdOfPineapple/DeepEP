E0 · Throughput against concurrency: SM or link?

Sweeping SM count and token count on the unmodified dispatch to find what bounds throughput now that E1 has shown the per-token wait is local.

experiment E0 · 21 configurations · 4 × H100 on host GPUs 4–7 · scripts: e0_sweep.py, common/run_dispatch.py, e0_analyze.py

1. Motivation

Each dispatch warp handles one token at a time: it loads the token into shared memory, issues one bulk store per destination, and at the top of the next iteration waits for those stores before it can reuse the buffer (tma_store_wait, dispatch.cuh:315). Before any measurement, the obvious reading of that loop was that a warp has at most one token in flight, and that the wait lasts until the peer GPU has the data, roughly an NVLink round trip of 1.3 µs. Under that reading, dispatch throughput would be bounded by (warps × 14 KB) / round trip, and the wait itself would be a per-token sensor of how congested the path to the peer is.

E1 showed the second half of that reading is wrong: the wait returns a few hundred ns after issue, as soon as the SM's copy engine has accepted the bytes, whether the destination is local or a peer. The round trip is never waited for inside the loop. So the question changes. If the per-token wait is not holding warps back for the round trip, what does bound throughput? Two candidates remain. One is the SM itself: E1 measured that one SM can push bulk stores to a peer at only about 50 to 58 GB/s, so with few SMs the kernel might be SM-bound. The other is the NVLink path out of the GPU, which saturates at some aggregate rate regardless of how many SMs feed it. The two predict different shapes when the number of SMs is swept: the first grows linearly with SMs, the second flattens. A second question is where a warp feels the pressure when the link is the limit, at the store instruction, at the wait, or nowhere visible at all.

This experiment sweeps the number of SMs (concurrency) and the number of tokens (work per warp) with uniform routing and the unmodified kernel logic, and reads the per-lane trace to see where a warp's time goes.

2. Methodology

In one sentence: run the unmodified dispatch at several SM counts and token counts, time it, and use in-kernel timestamps to see how long each part of a warp's loop takes.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 3 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: num_sms ∈ {2, 4, 8, 12, 16, 24, 32} (DeepEP's own model would pick 20) crossed with tokens per rank ∈ {256, 1024, 4096}, 21 configurations in all, each run as a separate invocation of the procedure. Routing is uniform (ratio 1) and the kernel is the baseline instrumented build.

2.2 How each reported number is computed

Every dispatch warp handles one token per loop iteration. For each token the kernel stamps the following moments: loop top (start of the wait for the previous token's stores), slot free (that wait returned), the slot atomic issued, token loaded into shared memory, all bulk stores issued, and per lane the moment its bulk store was issued and the moment its wait_group returned. SM 0 additionally stamps the kernel phases: entry, opening-barrier arrive and release, the notify phases, closing-barrier arrive and release. From these:

  • NVLink GB/s (Figure 1) = tokens this rank sent to other ranks × 14,464 bytes per token row ÷ kernel µs from step 4. "all-dest GB/s" counts local destinations too.
  • Slot wait = slot free − loop top. This is the tma_store_wait at the top of the loop, DeepEP's only per-token wait.
  • Slot-free to load-done = token loaded − slot free: the TMA load of the token, the top-k loads and the slot atomic.
  • Load-done to stores-issued = all stores issued − token loaded: the time the warp spends in the cp.async.bulk issue instructions themselves. This is where an issue stall shows.
  • Lane issue → done = per-lane wait return − per-lane store issue.
  • Atomic latency = per-lane atomic return − atomic issued.
  • Kernel phases (Figure 4): data plane = last dispatch warp's final stamp − opening-barrier release; closing barrier = closing-barrier release − that last warp stamp. Warp spread = last warp finish − first warp finish on a rank.

Durations are pooled over all tokens, all warps, all four ranks and the three traced repeats before percentiles are taken; "p50" and "p99" are over that pool. Kernel µs is the mean over ranks of the Kineto value.

2.3 Configuration

  • 4 ranks on host GPUs 4–7, hidden 7168 BF16, 256 experts (64 per rank), top-8, expert alignment 128, do_expand=True, CPU sync on. Measured destinations per token E[k] ≈ 3.6, so about 72 % of each GPU's traffic crosses NVLink. Each SM runs 4 notify warps and 15 dispatch warps.
  • Tracing costs +0.6 % of kernel time (median over configurations), from the probes-on Kineto run of step 4.

3. Results

Throughput is per-SM capacity times SM count until the NVLink path saturates at about 285 GB/s per GPU. At 4096 tokens per rank the kernel delivers 66 GB/s of NVLink traffic with 2 SMs (33 GB/s per SM, 44 GB/s per SM counting local destinations, consistent with E1's 50 GB/s per SM drain) and 268 GB/s with 16; adding SMs beyond 12 buys about 10 % more while the slot wait grows threefold. Small token counts never reach the plateau: with 256 tokens per rank most warps handle one token and the barriers dominate.
Where a warp's 17 µs iteration goes, and where back-pressure shows. With 2 to 8 SMs a warp spends about 3.7 µs in the slot wait, 4.6 µs from slot free to load done (TMA load of x, top-k loads, the slot atomic at 96 ns), and about 8.7 µs between load done and stores issued. That last segment is almost pure cp.async.bulk issue stall: E1 showed the per-lane queue admits about seven stores and the SM drains them at ~50 GB/s, and fifteen warps share that path. So the quantity that limits how far a warp can run ahead is the SM's bulk-store queue, about seven stores per lane, and the first place back-pressure appears is the store instruction. Past 8 SMs the aggregate issue capacity exceeds the NVLink path and the queueing moves into the slot wait: its p50 grows from 3.7 to 9.7 µs and its p99 from 5 to 36 µs at 32 SMs. The slot wait is therefore a usable congestion sensor, with this meaning: it reports the sender's queue towards the link, not the state of the peer.

4. Conclusions

  1. What bounds throughput. Throughput is min(per-SM bulk-store drain × SMs, NVLink path), about 33 GB/s per SM and 285 GB/s per GPU here. The limit on how far a warp can run ahead is the SM's async-proxy queue (about seven stores per lane), not one token per warp waiting for a round trip; the queue drains at the per-SM rate, so a warp spends half its iteration stalled on the store instruction even on an idle fabric. The pre-measurement model "warps × 14 KB per round trip" is withdrawn. Link saturation adds queueing that is visible in the slot wait and the per-lane wait, with p99 values of tens of µs.
  2. The tail is large. The first and last dispatch warp of a rank finish 245 µs apart at 16 SMs (data plane 539 µs), and the closing barrier then waits a further 54 µs for the slowest rank. Roughly half the data-plane span is therefore a tail in which the fabric drains while most warps are already idle. The opening barrier of the traced runs also records raw launch skew between ranks of hundreds of µs to ms when no host barrier precedes the launch.
  3. Slot atomics are not a bottleneck at four ranks: 96 ns p50 at every concurrency, p99 128 ns. The concern that all 15,000 slot-allocation atomics serialise on one cache line is real but cheap at this scale; E3 quantifies the padded layout anyway.
  4. Concurrency has a cost beyond the plateau. More SMs than the link needs lengthen the slot wait and the closing-barrier tail without adding throughput. DeepEP's own choice (20 SMs here) sits near the knee.
  5. The per-lane trace is validated as a tool. About 1 % overhead, and it separates the warp iteration into its parts. The slot wait is the quantity to watch in E2, where routing skew replaces concurrency as the stressor.
  6. Small-token runs are barrier-bound, which is the decode regime (few tokens per rank, kernel time dominated by synchronisation rather than data); the SM-level timeline already shows the opening barrier and the closing wait as the dominant phases there.
Limits. Four ranks, one node; E[k] ≈ 3.6 so the fan-out per token is smaller than with eight ranks. Kineto timings include DeepEP's L2 flush and barrier per iteration, as in its own test. The per-SM issue capacity of 58 GB/s comes from a single-destination microbenchmark; here each warp fans out to up to four destinations.
