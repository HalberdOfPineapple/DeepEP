E7 · The tail: scheduling, routing or path?

Regress each dispatch warp’s finish time on its token count, store count and hot-rank stores, under uniform and skewed routing, to see how much of the tail is knowable before launch.

experiment E7 · 11 runs · 4 × H100 on host GPUs 4–7 · scripts: e7_sweep.py, E2 base runs, e7_analyze.py · generated 2026-10-13 17:32

1. Motivation

E0 found that on a rank the first and last of the 240 dispatch warps finish about 240 µs apart in a 540 µs data plane, and that the closing barrier then waits for the slowest rank. The last warp's finish is what the whole dispatch waits for, so the tail is the critical path. There are three candidate reasons for one warp to finish late: it was given more work (the static token assignment gives some warps one token more than others), its tokens had more destinations or went to a congested destination (routing), or its stores happened to wait longer on the path (the SM's queue, the link, the peer). The first two are known to the library before the kernel runs; the third is only knowable by measurement. If the tail is mostly the first two, a scheduler can fix it; if it is the third, a tool has to find the path.

2. Methodology

In one sentence: for every dispatch warp, take its finish time from the trace and count its tokens, its stores and its stores to the hot rank, then ask how much of the spread of finish times a linear fit on those counts explains, under uniform and skewed routing.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 3 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: the routing ratio (1, 1.5, 2, 3, 4, from E2's base runs) and the random seed (two extra seeds at ratios 1 and 3, run here), plus two runs with the physical SM id recorded. 16 SMs, 4,096 tokens per rank.

2.2 How each reported number is computed

  • Warp finish = the warp's last wait_group return (WARP record) − the opening-barrier release on that rank, in µs. Data plane = the latest finish on the rank.
  • Tail fraction = (latest finish − median finish) ÷ latest finish, per (rank, repeat), median over them.
  • Per-warp work: tokens handled, bulk stores issued (sum over its tokens of the number of distinct destination ranks, from the destination mask), stores into rank 0 (the hot rank when ratio > 1).
  • Variance explained: within each (rank, repeat) an ordinary least-squares fit of finish on the work counts; 1 − residual sum of squares ÷ total sum of squares, pooled over (rank, repeat). "tokens only" uses the token count; the second fit adds stores and hot-rank stores. A third fit uses only the warp's block (the SM the block runs on): the group mean per block.
  • Physical SM: two extra runs (ratios 1 and 3) with the warp record extended by %smid, the hardware SM number, so that block → SM placement can be read instead of assumed.

2.3 Configuration

  • 4 ranks on host GPUs 4–7, 16 SMs, 4,096 tokens per rank, top-8 of 256 experts, baseline instrumented kernel.

3. Results

The warp’s own work explains nothing; the SM it runs on explains almost everything. Under uniform routing the tail is 21 % of the data plane, and a fit on tokens, stores and hot-rank stores explains 1 % of the finish-time variance (every warp has 17 or 18 tokens and nearly the same number of stores). A fit on the warp’s block alone explains 89 %. The 15 warps of a block finish together, and blocks fall into two or three discrete levels, about 306 to 585 µs on rank 1. The levels are identical across repeats, seeds and the E0/E2 runs on the same GPU, and different from GPU to GPU. The same holds at every ratio (table).
It is the physical SM, in TPC pairs. Recording %smid shows that the cooperative launch places the 16 blocks on the same physical SMs every time (SMs 124–131 and 0–7 on these GPUs), two blocks per TPC, and that the finish level is a property of the TPC: both SMs of a pair sit at the same level, and the slow pairs of one GPU are not the slow pairs of another (Figure 4). The ratio between the slowest and the fastest pair is about 1.4 on the GPUs with three levels. Since each block's warps store the same amount of data to the same destinations, the difference is in the drain rate from that SM towards NVLink, upstream of the ports, which are shared equally by all blocks.

4. Conclusions

  1. The tail is not scheduling and not routing; it is where the block landed. Token count, store count and hot-rank stores explain almost none of the spread; the block identity explains almost all of it, and the block identity maps to a fixed physical TPC whose drain rate towards the fabric is 1.0, 1.2 or 1.4 times another's. That is a location attribution at the sender, inside the SM-to-port path that the frame of the analysis note marks as dark, and it was reachable with one extra register read per warp.
  2. It is stable, so it is actionable. Because placement and per-TPC speed repeat run after run, a dispatcher could measure them once and either hand fewer tokens to the slow TPCs or request different SMs; the data plane would shrink towards the fast level, up to about 30 % here.
  3. Skewed routing does not change the picture. Hot-rank stores do not predict a warp's finish at any ratio in this four-rank setup; the per-TPC levels remain.
  4. What the cause is remains open. The per-TPC levels could be the TPC's share of its GPC's crossbar bandwidth, the L2 slice affinity of the receive-buffer addresses the block happens to write, or a difference in how the async proxy of each TPC is served. Distinguishing them needs an address sweep per TPC (E10) and a GPC map of these GPUs.
Limits. Four ranks (at most 4 destinations per token, so little variation in stores per warp); a linear fit; only 16 of the 132 SMs are exercised, in two GPCs, so the TPC levels seen are a sample. Finish is the warp's last local acceptance, not the arrival at the peer.
