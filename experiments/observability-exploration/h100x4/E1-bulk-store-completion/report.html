E1 · What "complete" means for a bulk store to a peer GPU

Calibrating the one per-token event DeepEP's data plane has: is cp.async.bulk.wait_group a round trip or a local hand-off, what guarantees remote visibility, and how far ahead of the link can one SM run.

experiment E1 · 2026-10-12 22:35:14 · 4 × NVIDIA H100 80GB HBM3 on host GPUs 4,5,6,7 · scripts: e1_bulk.cu, e1_run.py, e1_analyze.py

1. Motivation

DeepEP's dispatch warps move every token with cp.async.bulk stores from shared memory into a peer GPU's buffer and then execute cp.async.bulk.wait_group 0 before reusing the slot (dispatch.cuh:283). Before measuring, two things were assumed about that wait: that it is the kernel's only flow control, holding each warp to one token in flight until the peer has received it; and that its duration could serve as a per-destination congestion sensor, since a slow peer would make the wait longer. Both depend on what the hardware means by "complete" for a bulk store whose destination is another GPU. PTX documents completion as the writes being performed, but not whether that is acceptance by the local memory system or acknowledgement from the peer. Every later experiment reads the per-lane wait duration from the trace, so its meaning had to be settled first.

Three questions: (1) does wait_group wait for the NVLink round trip; (2) what does guarantee remote visibility, and what does it cost; (3) how many bulk stores can one SM push without the issue path blocking, which is the hardware's own window.

Terms used in this report

Bulk store. cp.async.bulk copies a block of bytes (here one 14 KB token) from an SM's shared memory to an address in global memory. When that address belongs to a peer GPU, the bytes travel over NVLink. The instruction returns immediately; the copy is carried out later by a hardware engine on the SM (the "async proxy", the same unit that serves TMA).

wait_group. Because the copy is asynchronous, the thread needs a way to ask "is it done yet?" so it can reuse the shared-memory buffer. cp.async.bulk.commit_group closes a batch of stores and cp.async.bulk.wait_group 0 blocks until all batches are "complete". E1's first question is what "complete" means when the destination is another GPU: has the data merely left the SM, or has it arrived at the peer?

The flag. A flag is a small word (4 or 8 bytes) in the receiver's memory that the sender writes after the data, as a signal meaning "the data is there, you can read it". The receiver does not know when data will arrive, so it spins on the flag. This data-then-flag pattern is how all of DeepEP's communication works: dispatch warps write tokens with bulk stores, and later the per-slot counters, the token counts written by the notify warps, and the closing barrier word play the role of the flag; the receiving rank reads the tokens only after it has seen them.

"A flag stored after wait_group alone". The sender's sequence is: bulk store the data, execute wait_group 0, then store the flag, with nothing else in between. If wait_group meant "the data has reached the peer", this sequence would be safe. The visibility probe shows it is not: the flag, a tiny scalar store, can reach the receiver before the 14 KB payload, so the receiver sees the flag and then reads bytes that are still from the previous round. Those are the stale chunks in the table. Inserting fence.acq_rel.sys between the wait and the flag, or writing the flag with release semantics (which is what DeepEP's red.release.sys barrier does), makes the hardware hold the flag until the data is visible, and the stale count drops to zero.

Why it matters for observability. The only per-token completion event the sender can observe cheaply is wait_group, and it reports local acceptance, not arrival. Anything that wants to measure per-token delivery time at the sender therefore has nothing to read; the event that does reflect the peer (the fence or release) costs a full NVLink round trip and is executed once per kernel, not once per token.

2. Methodology

In one sentence: outside DeepEP, write small CUDA kernels that do exactly one bulk store (or one flag exchange) between two GPUs, time it on the GPU's own clock, and vary what the sender waits on.

2.1 Procedure

  1. Build. e1_bulk.cu is compiled once with torch.utils.cpp_extension into a module exposing the probe kernels below. One Python process (e1_run.py) drives all four GPUs; peer access is enabled between every pair so a kernel on GPU A can hold a plain pointer into GPU B's memory, the same address class DeepEP uses over NVLink.
  2. Allocate. On every GPU a 64 MB destination buffer and a few flag words.
  3. Latency probe. For every destination GPU (including the source itself, the "local" case), every wait variant (six, listed under 2.2) and every store size (1 KB to 64 KB): launch one warp that repeats 2,000 times: fill a shared-memory buffer, read %clock64, issue one bulk store to the destination, commit, do the wait variant, read %clock64 again. The first 200 repeats are discarded as warm-up; the rest give the issue-to-return distribution for that cell.
  4. Concurrency probe. The same kernel with 1, 4, 8 and 15 warps on one SM, then 15 warps on 1 to 16 SMs, all storing 14,464-byte tokens to one peer, to see how the per-store wait and the delivered rate change as more stores share an SM and a link.
  5. Issue probe. One lane issues 512 bulk stores back to back with no wait at all, stamping the clock after each issue instruction. A jump in the gap between consecutive stamps shows the point where the hardware stops accepting new stores.
  6. Ping-pong. For every ordered GPU pair, one thread on each side: A writes a flag into B's memory, B spins until it sees it and writes back into A's memory, A spins; 10,000 rounds, each side stamping %globaltimer at send and receive. This gives the round-trip time and, PTP-style, the offset between the two GPUs' clocks.
  7. Visibility probe. Described in the primer above: 2,000 rounds per (wait variant, size) of data store, wait, flag store on GPU 4; spin on flag, read data, count stale chunks on GPU 5.
  8. Analyse. Everything is written to results/e1_results.json; e1_analyze.py computes the percentiles and draws the figures.

2.2 Probe details and definitions

  • Hardware. NVIDIA H100 80GB HBM3 × 4 (host GPUs 4,5,6,7), NVLink through four NVSwitch chips. GPUs 0–3 of the node were busy with another job during the run; its NVLink counters stayed at zero throughout (see common/logs).
  • Latency probe. One warp per slot. Lane 0 issues one bulk store of B bytes from a shared-memory buffer to the destination, commits the group and waits with one of the variants above; the warp reads %clock64 before the issue and after the wait. Cycles are converted to ns with the slot's own (clock64, globaltimer) pair measured over the whole run. Mode 4 replaces the bulk store by 32 lanes of 16-byte st.relaxed.sys followed by a system fence, the pattern DeepEP's notify warps use for the count stores.
  • Concurrency. The same probe with 1, 4, 8, 15 warps on one SM and with 15 warps on 1 to 16 SMs, all to one peer; the issue rate is warps × bytes / mean wait, the delivered rate is total bytes / (time to the end of the final wait_group), which includes the drain of whatever the waits did not cover.
  • Issue probe. One lane issues 512 bulk stores back to back with no wait, recording the cycle after each issue; a knee in the issue timestamps would be the point where the hardware stops accepting.
  • Ping-pong. Two single-thread kernels on two GPUs exchange 4-byte flags with st.relaxed.sys and ld.acquire.sys; 10,000 rounds per ordered pair give the round-trip time and a PTP-style offset between the two GPUs' %globaltimer clocks. Offsets around every triangle of GPUs are checked for consistency.
  • Visibility probe. The sender writes pattern i with a bulk store, performs one wait variant, then stores a flag; the receiver spins on the flag and immediately counts 16-byte chunks that do not yet hold i. 2,000 rounds per (variant, size).

3. Results

wait_group does not wait for the peer. For a 14,464-byte store the p50 from issue to the return of wait_group 0 is 367 ns to local memory and 372 ns to a peer GPU. Adding fence.acq_rel.sys raises both to about 1962 ns and 1972 ns, close to the ping-pong round trip of 1280 ns. wait_group.read is within a few ns of wait_group. The NVLink hop is invisible to the wait and visible to the fence.
A flag stored after wait_group alone can arrive before the data. With plain wait_group 0 the receiver found stale payload after seeing the flag in 76 of 6000 rounds (up to 240 chunks of a 4 KB store still old); with fence.acq_rel.sys after the wait, in 0. DeepEP's closing barrier is correct because its red.release.sys carries release semantics; the tma_store_wait before it only guarantees that the async proxy has finished reading shared memory and handing the bytes on.

Issue blocks after about seven stores; the back-pressure point is the store instruction, not the wait. One lane issuing 14,464-byte bulk stores back to back pays 110 ns per issue for the first 8 stores and then 229 ns per issue to local memory, 285 ns to a peer: the async proxy accepts a handful of stores and thereafter admits one only when one drains. That pace is 63 GB/s local and 51 GB/s to a peer, per SM, and matches the delivered rates in the concurrency sweep (50 GB/s per SM with 4 to 15 warps). Sixteen SMs deliver 352 GB/s into a single peer, where the link saturates and the per-store wait p99 jumps to 30 µs.

Clock alignment between GPUs

The ping-pong gives a round trip of 1280 ns p50 between any pair, and %globaltimer offsets between GPUs that are large (hundreds of ms to seconds) but stable to tens of ns within a run. Around every triangle of three GPUs the three pairwise offsets close to within 768 ns (median 352 ns). That is the error bar for cross-GPU timestamps in E4 and E6: one calibration per session, about 100 ns, no per-kernel handshake.

4. Conclusions and what they change

  1. Can the sender observe per-token delivery? No. wait_group is a local-acceptance event. Its duration measures the depth of the local async-proxy / memory-system queue in front of this SM, not the state of the link or the peer. In the lane trace of E2, "issue → done" is therefore a sender-side congestion signal. Per-destination information survives only insofar as the local queue is shared across destinations, which E2 tests.
  2. What limits how far a warp runs ahead. DeepEP's loop does not wait a round trip per token. The limit is the per-SM async-proxy queue: about seven bulk stores per lane, drained at roughly 50 GB/s per SM to a peer. Back-pressure therefore reaches a dispatch warp first at the cp.async.bulk issue (the instruction stalls) and only secondarily at wait_group; with 16 SMs the aggregate issue capacity (~800 GB/s) exceeds the link, so the link's back-pressure shows up as queueing inside the SMs, visible as the slot wait and issue stalls. The pre-measurement model in which throughput is warps × one token per round trip is withdrawn; E0 measures the corrected version on the real kernel.
  3. Remote completion has exactly one cheap witness: a system-scope release. It costs a round trip (1972 ns) and serialises the issuing thread, so it cannot be inserted per token without changing the kernel. A per-destination completion counter (as GIN provides for the NIC path) is the missing hardware primitive for the NVLink path.
  4. Correctness note for anyone adapting the pattern. Data-then-flag over NVLink needs the release on the flag or a system fence; wait_group (either variant) is not enough. The visibility probe makes this reproducible in seconds.
  5. Cross-GPU clocks on one node are usable with a one-time calibration (triangle closure about 352 ns), which E4 and later experiments rely on.
Limits. Peer pointers here come from CUDA peer access, not from an NCCL window; the address class and path are the same, the allocation is not. Timings are from a single SM clock converted to ns; p50 values repeat exactly across sizes because the async proxy's acceptance cost is deterministic at this resolution.
