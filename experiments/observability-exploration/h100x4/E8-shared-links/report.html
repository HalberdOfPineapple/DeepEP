E8 · Two kernels on the same links

Dispatch beside a concurrent combine or a NCCL all-to-all: what each pays, what the stamps show, and what only the link counters can attribute.

experiment E8 · 8 runs · 4 × H100 on host GPUs 4–7 · scripts: e8_sweep.py, common/run_dispatch.py (--overlap, --nvml), e8_analyze.py · generated 2026-10-13 17:34

1. Motivation

In a pipelined MoE layer the dispatch of one micro-batch runs while the combine of another is still in flight, and both share the GPU's NVLink ports with whatever else the process, or another process on the same GPU, is sending. When two kernels share links, each one's duration grows, but neither has any way to see the other: the dispatch's own stamps show stores taking longer, not why. The question is what the sharing costs each kernel, whether the per-lane stamps of the traced kernel change in a way that distinguishes "another kernel is on my links" from "my own fan-out saturates them" (E0) or "one destination is hot" (E2), and whether link-level counters outside the kernel can supply the missing attribution.

2. Methodology

In one sentence: run the traced dispatch alone, then with a DeepEP combine on a second buffer running at the same time, then with a queue of NCCL all-to-all collectives running at the same time, and compare the dispatch's stamps, the other kernel's duration, and the per-link byte counters.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. The baseline instrumented build is used throughout. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 5 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: what runs on the side stream during each traced dispatch: nothing; a DeepEP combine on a second buffer; six NCCL all-to-all calls of 64 MB; sixteen of them. The side-stream work is enqueued right before the barrier that precedes the dispatch, so it is already running when the dispatch starts. NVML link counters are read by rank 0 on all four GPUs before and after each repeat. The Kineto step is skipped.

2.2 How each reported number is computed

  • Dispatch data plane, tail, kernel span from the SM 0 and warp stamps as in E0 (median over ranks and repeats). C1 slot wait, C3 issue and per-lane store latency pooled over all ranks, warps and repeats.
  • Other kernel's time: CUDA events on the side stream around one combine call (alone: before the repeats; overlapped: in each repeat), or around the whole NCCL queue (alone: one call × count; overlapped: the queue).
  • Per-link bytes: NVML NVLINK_THROUGHPUT_DATA_TX/RX per link, after minus before, per repeat, per GPU; the figure shows GPU 4. The spread across links (coefficient of variation) says whether the traffic is balanced over the 18 links.

2.3 Configuration

  • 4 ranks on host GPUs 4–7, 16 SMs per DeepEP kernel, 4,096 tokens per rank, uniform routing, CPU sync on. NCCL all-to-all through a second process group with 64 MB buffers.

3. Results

A concurrent combine costs little; a concurrent NCCL all-to-all doubles the dispatch. Dispatch data plane: 537 µs alone, 543 µs beside combine, 1165 µs beside six all-to-alls, 1161 µs beside sixteen. The per-lane store latency p50 goes from 4.9 to 4.9 / 6.2 / 6.1 µs and the slot wait p99 from 15 to 15 / 55 / 54 µs. The combine takes 806 µs alone and 871 µs beside the dispatch.
The signature is the same as link saturation by the dispatch’s own fan-out. Longer slot waits and longer per-lane waits, uniformly across destinations, are exactly what E0 shows when the SM count is raised past the link’s capacity. Nothing in the dispatch’s stamps says that another kernel is the cause. The per-link counters do: the TX bytes on GPU 4 per repeat rise from the dispatch’s own share to the sum of both kernels (table), and they are spread evenly over the 18 links in every case, so the sharing is on every port, not on a few.
The monitor perturbed the measurement. The first set of runs read the NVML per-link counters on rank 0 a few tens of ms before each launch. With that read the dispatch's data plane was 673 µs instead of 537 µs and the opening barrier showed 100–400 µs of launch stagger between ranks; the effect lasts about a millisecond after the read, so cases whose side-stream launch took longer than that (combine) were not affected. The timing comparisons above therefore use repeated runs without the read, and the counter runs are used only for the per-link byte distribution. For a tool, this is a measurement in itself: an NVML field-value query is not a free observer of a sub-millisecond kernel.

4. Conclusions

  1. Who pays depends on the kernels, and the loser cannot tell. Beside a combine on another buffer, both DeepEP kernels keep their time to within 10 % (the two together stay under the link capacity); beside a NCCL all-to-all the dispatch's data plane doubles while the all-to-all queue slows by about a third. From inside either kernel the slowdown is indistinguishable from the kernel’s own link saturation (longer slot waits and per-lane waits, uniformly over destinations). This is the clearest case for a signal outside the kernel.
  2. Observers are not free. An NVML counter read before the launch cost the dispatch about 20 % and hundreds of µs of launch stagger; a tool must either read counters from the GPU or place host reads where their effect has decayed.
  3. Link counters give the attribution, at coarse time resolution. Per-link byte deltas over the kernel show whose bytes were there; what they cannot give is when within the kernel, because one NVML read of four GPUs takes milliseconds. A per-link byte counter readable from the GPU, or sampled at tens of µs, would turn this into a per-phase attribution.
  4. Dispatch and combine on separate buffers co-exist without deadlock on this build, at the cost measured here; the pipelined-MoE overlap is therefore a scenario the traced kernel can be run in directly.
  5. Balanced links. In all cases the 18 links of a GPU carry equal shares (CV of a few percent), so on this node the address-to-link mapping does not concentrate either kernel’s traffic; a link-level hot spot is not among the causes to look for here.
Limits. Four ranks; the combine is replayed from one fixed handle; the NCCL traffic pattern is a plain all-to-all; NVML resolution is per repeat, not per phase; the other kernel is not traced, so its own phase decomposition is not available.
