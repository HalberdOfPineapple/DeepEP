E2 · Destination incast and victim flows

Making one rank hot with DeepEP's unbalanced-gate generator and reading, on the other senders, whether their stores to idle ranks slow down too.

experiment E2 · 10 runs · 4 × H100 on host GPUs 4–7 · scripts: e2_sweep.py, common/run_dispatch.py, common/apply_trace_patch.py (--wait-read), e2_analyze.py

1. Motivation

When one rank hosts popular experts it receives several times the traffic of the others (incast). The concern is that this slows traffic to the idle ranks as well, so that one hot destination degrades the whole dispatch rather than only its own share. Two mechanisms could do that. Warp-level: each dispatch warp waits for all of its lanes' stores before reusing its slot, so a slow store to the hot rank blocks the warp's next token, including its stores to idle ranks. Fabric-level: if the sender's NVLink egress credits or the switch queues are shared across destinations, stores to idle ranks physically queue behind stores to the hot rank. E1 and E0 refined the picture: the per-token wait returns when the SM's copy engine has accepted the store, not when the peer has it; the queue that actually limits a warp is the per-SM async-proxy store queue; and that queue is shared by all destinations an SM's warps store to. The question for E2 is therefore which sharing shows up under incast: does the completion time of stores to idle ranks, as seen on the sender, rise when another destination is hot, and does releasing the slot earlier (wait_group.read) change anything.

2. Methodology

In one sentence: make rank 0 the hot destination with DeepEP's unbalanced routing generator, and on every other rank compare how long its stores to rank 0 take against how long its stores to the two idle ranks take, using the per-lane stamps.

2.1 Procedure

  1. Build the kernel under test. common/apply_trace_patch.py takes the unmodified DeepEP dispatch kernel and inserts timestamp probes: at a handful of places a thread reads the GPU's nanosecond clock (%globaltimer) and writes it to a trace buffer in global memory. Here the patch is applied twice: once as the baseline, once with the --wait-read flag, which swaps the loop-top wait for the .read variant and changes nothing else. The kernel logic is otherwise unchanged. DeepEP compiles it just in time on first use.
  2. Start four processes, one per GPU 4–7. Each creates a DeepEP buffer, draws 7168-wide random BF16 tokens and random top-8 routing (DeepEP's own generator, so the routing statistics match its tests), and allocates the trace buffer. The trace buffer is handed to the kernel through an existing optional argument whose allocation is made larger than the kernel expects.
  3. Warm up. Three dispatches, so that JIT compilation and first-touch page mapping are out of the way.
  4. Measure kernel time with the probes off. 20 dispatches under the Kineto profiler, the same method DeepEP's test suite uses: before each one the L2 cache is flushed and the four ranks synchronise with an all-reduce, so each dispatch starts cold and together. The profiler reports the duration of the dispatch kernel on each GPU; the "kernel µs" in every table is that duration. The run is then repeated with the probes on to measure their overhead.
  5. Record 3 traced dispatches. For each one: measure the clock offset between every pair of GPUs (a 400-round ping-pong through shared memory, so that stamps from different GPUs can be compared), zero the trace buffer, synchronise, run one dispatch with the probes on, copy the trace buffer to the host, and measure the clock offsets again. The two offset measurements bracket the dispatch; their mean is used, and their difference bounds the clock drift during the dispatch.
  6. Analyse. All ranks' traces and kernel times are saved to one .pt file. The analysis script turns stamp pairs into durations (definitions in 2.2 below), pools them over ranks, warps and repeats, and draws the figures.

What varies here: the routing ratio ∈ {1, 1.5, 2, 3, 4} passed to DeepEP's get_unbalanced_scores(..., precise=True), which makes rank 0 receive ratio × the tokens of each other rank; and two kernel builds, the baseline and one with cp.async.bulk.wait_group.read 0 at the loop top. Ten runs of the procedure in all.

2.2 How each reported number is computed

  • Per-destination latency (Figure 2): for every lane of every dispatch warp on a sending rank, wait return − store issue, grouped by the destination rank that lane recorded. "hot" is the group with destination rank 0; "idle" pools the two destinations that are neither rank 0 nor the sender. Medians are over all lanes of the three non-hot senders and the three repeats.
  • Hot-rank intake = bytes stored into rank 0 by all senders ÷ (last store to rank 0 − first store to rank 0), stamps aligned with the per-run clock offsets.
  • Completion time of the last store to an idle rank (Figure 3): on each sender, the latest wait-return stamp among stores to idle destinations, relative to the opening-barrier release, compared with the same for the hot destination.
  • Kernel µs and tracing overhead as in step 4.

2.3 Configuration

  • 4 ranks on host GPUs 4–7, 4,096 tokens per rank, top-8 of 256 experts, 16 SMs (DeepEP's own choice is 20; 16 keeps the aggregate per-SM issue capacity near the link so that sender saturation does not mask destination effects), expert alignment 128, CPU sync on.
  • With four ranks the generator caps destinations per token at min(8, 4, ⌊3/ratio⌋ + 1): 4 at ratio 1, 2 at ratio 1.5 to 3, 1 at ratio 4. Ratio 4 therefore is the single-destination case (every token goes to exactly one rank), which also removes the warp-level coupling by construction.

3. Results

The hot rank's intake saturates at about 321 GB/s and sets everyone's kernel time; the other senders run at 159 GB/s, 59 % of what they do in the balanced run. The generator changes the total traffic with the ratio, so kernel times are not comparable across ratios; the rates are. Rank 0's NVLink intake rises from 268 GB/s (balanced, where each rank's intake equals its egress) to 321 GB/s and stays there, while each non-hot sender's egress falls to 159 GB/s. The link into one GPU, at roughly 320 GB/s delivered, is the resource that is full.
A sender cannot tell its hot destination from its idle ones. On the non-hot senders, lane issue → wait return towards the hot rank is 4.8 µs p50 at ratio 1 and 4.7 µs at ratio 4.0; towards idle ranks 4.8 µs and 4.9 µs. At every ratio the two are equal to within 0.2 µs, and both tails grow together (p99 13 µs → 31 µs). The per-SM async-proxy queue that E1 identified is a FIFO shared by every destination an SM's warps store to: when the hot rank's intake throttles the stores addressed to it, every store queued behind them waits the same time, whatever its destination.
Consequence: the idle destinations' stores are spread over the whole kernel instead of finishing early. On sender rank 1 at ratio 4.0, the last store to an idle rank completes at the same time as the last store to the hot rank (Figure 5, right), and the idle ranks' data planes end within 168 µs of the hot rank's. This is sender-side head-of-line blocking: a receiver bottleneck becomes a uniform slowdown of all of the sender's traffic, and the idle ranks' intake, which could have finished at 268 GB/s, drips in at the hot rank's pace. The "idle ranks finish early and wait at the barrier" picture in the analysis note is wrong for this hardware; the closing-barrier wait on non-hot ranks is only 15 µs at ratio 4.0.
Releasing the slot earlier does not help, and deepens the queue. The wait_group.read variant changes kernel time by +0.2 % at ratio 4.0 and by +0.2 % balanced, while its per-lane p99 at ratio 4.0 rises to 71 µs (baseline 31 µs): more stores sit in the same saturated queue. The warp-level coupling of problem P1 is real but is not where the time goes.

4. Conclusions

  1. Incast is paid by every sender, uniformly, through the shared per-SM store queue. The hot rank's intake caps near 320 GB/s; each sender's queue fills with stores to it, and stores to idle ranks behind them wait equally. Fabric-level victim flows in the switch cannot be excluded, but they are not needed to explain the data: the sender's own FIFO already produces the victim effect.
  2. Observability consequence. The one per-token signal a sender has, the local-acceptance wait, carries no destination information, because the queue it measures is shared. Attribution to a destination needs either the destination mix of what is queued (which the trace provides, since the library knows every store's destination) or a receiver-side ingress counter per source, which does not exist. A per-destination queue in hardware, or per-destination issue throttling in software, would turn the same trace into a per-destination signal.
  3. Which mechanism it is. The "warp-level" mechanism exists but is cheap (wait_group.read changes nothing); the "fabric-level" mechanism exists in a form not anticipated before measuring: sender-side FIFO sharing in the SM's async proxy, upstream of the link. The experiment that would separate it from switch-level sharing is to issue the hot and idle destinations from disjoint SMs; that is a kernel change, left for later.
  4. Mitigation hint for DeepEP. Since the hot rank's intake is the bottleneck and everything else queues behind it, scheduling tokens so that stores to the hot rank are issued last (or from a dedicated subset of SMs) would let idle-destination traffic finish early and shorten the tail of the combine that follows; the trace from this build is what would evaluate that.
Limits. Four ranks: at most three senders converge on the hot rank and at most two idle destinations exist per sender; the generator forces single-destination tokens at ratio 4. Per-destination latencies are local-acceptance times (E1), so they bound what any sender-side method can see. 16 SMs rather than DeepEP's default 20.
