01b · Memory map

The big picture: what lives where

Before the line-by-line sections, this is the whole memory picture for one dispatch on one GPU (rank 5 as the receiver, rank 1 as the sender). Every buffer, counter and staging slot in the later sections fits into one of the boxes below.

M.1 One GPU's memory during dispatch

Four rules explain almost every design choice in the kernels:

  1. Shared memory is per SM. Fast and private, so it holds per-SM scratch: the notify counters and one staging slot per warp. Anything that must be combined across SMs has to go through HBM. That is why phase C (§6.2) exists.
  2. HBM is one address space for the whole GPU, and atomics on it are serialized in the shared L2. Any SM can add to notify_reduction or to a sender slot counter and the result is consistent.
  3. Only the NCCL window can be written by other GPUs. Everything a peer must deliver (tokens, counts, barrier signals) lives there, at the same offset on every rank. PyTorch tensors are private: a peer never writes recv_x directly. The receiver's own copy epilogue fills it from the window.
  4. The CPU can only see pinned host memory. It spins on 40 numbers there rather than reading GPU memory, so it learns the output sizes without waiting for the kernel to finish.

M.1b The NCCL window in HBM, byte by byte

This zooms into the green "NCCL symmetric window" box of M.1. It is one allocation per GPU (ncclMemAlloc, §5), and every GPU's window has the same layout, which is why an offset computed on one rank is valid on every other rank.

Where EPSignals lives: two copies, created at buffer construction

EPSignals is only a layout; DeepEP applies it to two separate allocations. The kernel receives both pointers on every launch: context->workspace (GPU) and mapped_host_workspace (host) (ep.hpp:573-575). Its size is fixed by the maximum supported configuration (1,024 ranks, 2,048 experts, 1,280 channels), so it is 15,831,168 B (15.1 MiB) whatever your job's shape. About 15 MiB of that is the two hybrid-only channel-tail arrays.

05b · Cooperation map

How the warps cooperate: what each produces, who uses it, how it travels

Read this before §6 and §7. It answers one question: where does everything the notify warps compute end up? The short version is that the notify warps never talk to the dispatch warps. Their results go to two later consumers: the CPU, and the copy kernel.

The final target of the notify warps. On every rank, notify SM 0 ends by producing three things for that rank's receive side:
  1. 40 numbers in pinned host memory (phase H): tokens from each of the 8 senders, and the padded row count of each of the 32 local experts. The CPU waits for these so it can call torch.empty for recv_x and the other outputs with the right sizes (§9).
  2. psum_num_recv_tokens_per_scaleup_rank[8] (phase I, warp 0): where each sender's tokens begin in the flat list of received tokens. The copy kernel uses it to turn "received token i" into "buffer row r, slot s" (§10).
  3. psum_num_recv_tokens_per_expert[33] (phase I, warp 1): the first recv_x row of each local expert. The copy kernel calls atomicAdd on it to give each (token, expert) pair its own row (§10).

There are also two by-products: num_unaligned_recv_tokens_per_expert, used for zero padding and returned in the handle, and the optional cumulative_local_expert_recv_stats. The dispatch warps in the same kernel read none of these. They get their slots from a separate atomic counter (§7.2), so they never have to wait for notify.

C.5 Why it is split this way

  • Why the dispatch warps do not wait for notify. Every sender gets a fixed region of 4,096 slots in every receiver's buffer, so a sender never needs to know a receiver's totals before writing. Waiting for notify would put a full NVLink round trip in front of the 39 MB of data per peer.
  • Why the receiver still needs counts. Without them, it cannot tell how much of each 4,096-slot row is filled, and the CPU cannot size recv_x. The expert counts also cannot come from the buffer itself: they are needed before any token is copied, to fix each expert's starting row.
  • Why the counts go to the CPU early. Phase H runs before the token data has finished arriving. The CPU allocation therefore overlaps with the data transfer instead of waiting for it. Without CPU sync (do_cpu_sync=False), the outputs are sized for the worst case and only the GPU prefix sums are used.
  • Why SM 0 on every rank does both jobs. Phase E sends this rank's counts out, and phases F–I process the counts that come in. They run on the same SM one after the other, because F cannot finish until every peer has done its E.

Why the packed atomic is correct and cheap.
  • One instruction carries both the count and the "I'm done" flag. Each red_add is a single atomic update of one 64-bit word. Once a reader sees the high half equal 16, all 16 contributions to the low half are in the same value it just read.
  • No fence is needed. With a separate sum word and counter word, every SM would need a fence between its two writes, and the reader would need two loads that could disagree.
  • No carry into the high half. A low half holds at most 4,096 tokens, which is far below 232.

Why does SM 0 still have work after everyone has added?

What red_add actually does. ptx::red_add(ptr, value) compiles to red.gpu.global.add.u64 [ptr], value. It means: atomically perform *ptr = *ptr + value in global memory, and return nothing.

  • Atomically: if 16 SMs add to the same address at the same moment, the hardware applies the 16 additions one after another. None is lost.
  • Returns nothing: the issuing SM gets back neither the old nor the new value, and is not told when its add has landed. It fires the request and moves on.

So after phase C, the correct total is being built up in memory, but no thread knows when it is complete. Each SM knows only that it has sent its own add, not whether the other 15 have. The totals are not the goal anyway: each one must be sent to the rank that needs it ("rank 5, I am sending you 2,715 tokens"). Someone therefore still has to do four things:

  1. wait until all 16 adds have landed;
  2. read the final value;
  3. send it to the right peer, exactly once;
  4. reset the word to 0 for the next dispatch.

That is all SM 0 does in phase D, and why only one SM does it:

  • Exactly once. If all 16 SMs read the total and sent it, each peer would receive the same number 16 times. One SM must own each send.
  • The rest of the work is tiny. It is 264 numbers per rank: 264 small stores to peers, then waiting for 264 incoming numbers. One SM's 128 notify threads are enough.
  • "SM 0" is arbitrary. Any single CTA would work; blockIdx.x == 0 is just the easiest one to name.
  • A grid barrier would be worse. Making everyone wait at this_grid().sync() would also stop the 15 dispatch warps on every SM, which are busy moving tokens. With the counter, only SM 0's 4 notify warps wait.

How SM 0 knows "all 16 have added": the packed word, step by step

Each SM adds (1 << 32) | count, which as a 64-bit number equals count + 4,294,967,296. When such values are added together, the high halves and the low halves add up separately (the low half never exceeds 4,096, so it never carries into the high half). After k SMs have added, the word is [ high: k | low: sum of those k counts ]. The high half counts arrivals; the low half is the running total, and both change in the same atomic operation.

What encode/decode does, and why it is needed

This solves a different problem from the packed word, one that appears only when counts cross to another GPU.

The problem: "0 tokens" looks the same as "not written yet". Each receiver's receive array starts as all zeros, with one 8-byte slot per sender. Sender rank 1 writes its count into slot [1] of rank 5's array with a single NVLink store, and rank 5 spins on that slot waiting for it. If senders wrote the raw count, rank 5 reading 0 could not tell whether:

  • rank 1 has not written yet, so rank 5 should keep waiting; or
  • rank 1 wrote "I am sending you 0 tokens", which is a real answer, so rank 5 should stop waiting.

A count can legitimately be 0, so 0 cannot also mean "nothing here yet". The code needs a "has been written" flag, and the encoding builds it into the value itself.

The fix: store −v − 1 instead of v.

// deep_ep/include/deep_ep/common/math.cuh
dtype_t encode_decode_positive(const dtype_t& value) { return -value - 1; }   // f(v) = −v − 1
bool    is_decoded_positive_ready(const dtype_t& value) { return value >= 0; }

f(v) = −v − 1 is its own inverse, f(f(v)) = v, which is why one function is used to both encode and decode:

Every real count, including 0, is stored as a negative number. An untouched slot is 0, decodes to −1, and fails the >= 0 test. The receiver needs just one load per check: decoded = f(ld_volatile(slot)); if (decoded >= 0) { /* decoded is the count */ }. The store is a single aligned 8-byte write, so a reader sees either the old 0 or the complete new value, never a mix.

Where it happens:

phase D (SM 0, sender)    total = 11                → encoded = f(11) = −12, kept in shared memory
phase E (SM 0, sender)    put_value(peer slot, −12)   // the ENCODED value goes over NVLink

The host copy uses the same trick for the same reason: the host zeroes its 40 slots before each launch, and the CPU must tell "not written yet" apart from "count is 0".

Why two different tricks? It depends on how many threads write each word

With many writers you have to count arrivals, because one write landing says nothing about the others. With one writer, "it was written at all" is enough, and the encoding expresses that without a second word.

One number, start to finish

"How many tokens rank 1 sends to rank 5":

  1. Phase B. Each of rank 1's 16 SMs counts its share of those tokens in its own shared memory: 170, 168, 171, …
  2. Phase C. Each SM does red_add(notify_reduction[5], (1<<32) | its_count) and moves on without waiting.
  3. Phase D. SM 0 polls notify_reduction[5] until the high half reads 16. It reads the low half, 2,715, encodes it as −2,716, and resets the word to 0.
  4. Phase E. SM 0 stores −2,716 into rank 5's receive slot [1] over NVLink.
  5. Phase F, on rank 5. Rank 5's SM 0 polls slot [1] until it decodes to ≥ 0, gets 2,715, and resets the slot to 0.
  6. Phases G–I. Rank 5 adds up its per-expert counts, writes the encoded counts into pinned host memory for the CPU, and computes the prefix sums the copy epilogue uses.

Step ③: atomicAdd, "give me the next free slot on that rank"

atomicAdd(p, 1) atomically adds 1 to *p and returns the value from before the add. Each caller therefore gets a different number: 0, 1, 2, … in the order the adds reach the L2.

  • Which counter: scaleup_atomic_sender_count[dst] in this sender's own EPSignals (rank 1's window, §5). There are 8 counters, one per destination. They are not on the receiver.
  • Who competes for it: every dispatch warp of rank 1, across all 16 SMs, that has a token for that destination. 240 warps share 8 counters.
  • Why that is enough: rank 1 is the only writer into "row 1" on every receiver (§7.0), so a counter local to rank 1 can hand out that row's slots with no coordination with other GPUs.

Why the slot is the old value: the counter is a ticket dispenser

Read counter[dst] as "how many slots of row my rank on rank dst have already been handed out". Because slots are handed out from 0 upwards with no gaps, that number is also the index of the next free slot. That is the invariant the code relies on:

counter[dst] == number of slots already taken == index of the next free slot

atomicAdd(&counter[dst], 1) does two things as one indivisible step: it returns the current value (the next free slot, which the caller now owns) and leaves the counter one higher (so the invariant holds for the next caller). Like a take-a-number machine: the number printed on your ticket is the one that was showing, and the display moves on to the next number.

Why the parity bit: one barrier, reused for every token

Why exactly one lane, and why __syncwarp

  • elect_one_sync() (PTX elect.sync, ptx.cuh:34-46) returns true in exactly one active lane. The barrier was initialized for 1 arrival per phase, so exactly one lane must arrive. If all 32 lanes arrived, the first one would already drop pending to 0, and the rest would count against later phases and complete them early.
  • Only that lane spins in try_wait. The other 31 lanes skip the if and wait at __syncwarp(), which also orders memory within the warp. When the warp moves on, every lane may use the bytes in the slot.

Why the wait sits exactly here

  • Issued early, waited late. The load starts at the top of the loop body (§7.1). Between issuing it and waiting, the warp does useful work: writing metadata, deduplicating, claiming slots and recording them (§7.2). That work overlaps the 14 KB copy.
  • Must precede the stores. The very next step is tma_store_1d(dst_ptr, tma_buffer…), which reads the slot and sends it to the peers. Without the wait, a peer could receive a partly loaded token.
  • Only the hidden bytes are tracked. The metadata (top-k ids, weights, source index) is written by the lanes themselves with ordinary stores. Those writes need no mbarrier; tma_store_fence() (line 329) makes them visible to the TMA store instead.

FP8 variant: more arrivals, same rule

With FP8, the 32 lanes also fetch the scale factors with cp.async and then each executes cp.async.mbarrier.arrive (§13.3). Without .noinc, that instruction raises pending by 1 immediately and arrives (−1) later, once that lane's scale copies finish. Pending goes 1 → 33 and only falls back as the copies complete. The elected lane's arrive.expect_tx must come after these (source comment at line 351). Otherwise its arrival could take pending from 1 to 0 before the scale-factor arrivals were registered, and the phase could complete with the scales still missing.

The same pattern elsewhere

The copy epilogue uses the identical handshake for its own slots: the load and arrive_and_set_tx are issued together right after choosing the token (dispatch_copy_epilogue.cuh:88-95), and the wait comes after the top-k indices have been read and the destination rows chosen (lines 126-129).

Note what the barrier does not do: it does not wait for the copy kernel, the CPU, or anything after it. Reusing the buffer safely in the next dispatch is the job of the next opening barrier.

The other paths, for comparison

  • Scale-up over RDMA (kIsScaleupNVLink = false): gin_barrier_wo_local_sync with the World team. All SMs first flush every GIN QP (so the RDMA puts have completed), a system-scope fence orders any direct NVLink writes, and a grid sync follows. Then SM 0 sends signal(SignalInc) to every rank on QP 0 and waits on each rank's signal (barrier.cuh:133-169).
  • Hybrid (scale-up and scale-out both > 1): SM 0 runs the scale-up barrier while SMs 1… run the scale-out (Rail team) GIN barrier in parallel. An extra grid sync is inserted on SM 0's side to match the scale-out side's internal sync. The source calls this "kind of hacky".

13 · FP8 dispatch

sf: the FP8 scale factors, end to end

The running example uses BF16, so sf is None and every kNumSFPacks > 0 branch is compiled out. This section switches to FP8 for the same token and shows what sf is and every place the kernel touches it.

13.1 What sf is

FP8 (float8_e4m3fn) can only represent magnitudes up to 448, so activations are stored as FP8 values plus one scale per block of channels. sf ("scale factors") holds those scales. The test helper shows the scheme: each token's 7,168 channels are cut into blocks of 128, and each block gets one FP32 scale.

deep_ep/utils/math.py: how the tests produce (x, sf)math.py:31-56
def per_token_cast_to_fp8(x):                                     # x: [T, 7168] bf16
    x_view = x_padded.view(m, -1, 128)                             # [T, 56, 128]: 56 blocks of 128 channels
    x_amax = x_view.abs().float().amax(dim=2).clamp(1e-4)          # [T, 56]: largest |value| per block
    x_fp8  = (x_view * (448.0 / x_amax.unsqueeze(2))).to(torch.float8_e4m3fn)   1
    return x_fp8.view(m, 7168), (x_amax / 448.0)                     2

def per_token_cast_back(x_fp8, x_scales):                         # the inverse, used to check results
    return (x_fp8.float().view(m, -1, 128) * x_scales.view(m, -1, 1)).bfloat16()  3
  1. Each block is stretched so its largest value becomes 448, then rounded to FP8 (1 byte per channel).
  2. The scale is amax / 448, one float per block. For our token, sf[37] is 56 floats.
  3. Recovering the activations: x ≈ x_fp8 × sf[block]. Whoever consumes recv_x (the expert GEMM) needs each row's own 56 scales, which is why they must travel with the token.

The kernel never dequantizes, and the host only checks that each element is 4 bytes. How many channels each scale covers is the caller's choice; DeepEP only sees "num_sf_packs packs per token".

13.5 What you get back, and where sf does not appear

  • Return value. Python re-packs the pair: recv_x = (recv_x, recv_sf) (ep.py:746). On rank 5 that is ([35,712, 7168] float8_e4m3fn, [35,712, 56] float32), ready for an FP8 grouped GEMM.
  • Combine has no sf. Combine inputs must be BF16 (README), so the token layout there has no scale area, and the EP buffer is sized by the BF16 combine layout.
  • Cached dispatch. The backward of combine is a cached dispatch, which takes a tuple in the same way. The README's combine_backward accepts BF16 or (fp8, sf) gradients.
  • Hybrid (multi-node) dispatch carries the scales the same way: they are part of the same token layout, forwarded over RDMA and then NVLink.
