Diagnosing a degraded memory-semantic operation

A structured procedure: signal points, baseline, phase location, per-phase attribution rules, confirmation by manipulation, and where it stops.

notes · method, grounded in experiments E0–E9 on h100x4 · 2026-10-13

A structured way to go from "this dispatch was slow" to an owner: which phase, which location, which cause. Written in the manner of FabricPerf's methodology section, with the difference that the signal points sit inside a production kernel rather than in a probe, and that the procedure is a decision tree validated by the ten experiments in experiments/observability-exploration/h100x4.

1. The object and the question

The operation under diagnosis is one memory-semantic collective, DeepEP's dispatch: every rank's warps write tokens straight into peers' memory with bulk stores, exchange counts with 8-byte stores, and synchronise twice with barrier words. FabricPerf asks "how long does a transfer take between two endpoints", and answers it by timestamping a probe transfer at five points. The question here is different: given that one such operation took longer than its baseline, which of its phases absorbed the excess, at which location along the path, and what caused it. The answer must name an owner, because the remedies differ: a scheduler, the host code, the routing, a neighbouring kernel, the placement of blocks on SMs, or the fabric itself.

Two facts from the experiments shape the method. The sender's only per-store event, cp.async.bulk.wait_group, returns when the SM's copy engine has accepted the store, not when the peer has it; and the receiver has no per-store event at all. So the path splits into a lit part, everything up to the SM's queue, where stamps attribute precisely, and a dark part, from the port to the peer's memory, where only inference is possible. The procedure is built to exhaust the lit part before concluding anything about the dark one.

2. Signal points

Every signal is recorded by a thread that already exists in the kernel, into a buffer passed through an existing kernel argument, at a cost of about 1 % of kernel time. Two things make the signals comparable: a per-run clock calibration between every pair of GPUs, bracketing each kernel (the clocks drift by milliseconds per hour, so a one-time calibration is wrong within minutes), and a host-to-GPU mapping good to about ±5 µs. Each derived quantity has a baseline from a quiet run of the same configuration; the diagnosis works on the excess over that baseline, never on absolute values.

What is deliberately not in the signal set: any counter read from the host during the kernel. One NVML field-value read perturbs the GPUs for about a millisecond and shifts launches by hundreds of µs, so link counters are read only before the barrier that precedes the launch and after the final synchronisation, and used as per-kernel byte totals.

3. The procedure

  1. Establish the baseline. Run the same configuration (ranks, tokens, SMs, routing) in isolation a few times with the signals on. Record the median of every derived quantity in Figure 1, including the per-TPC finish levels of this GPU, which are a fixed property of its placement.
  2. Record the degraded operation with the same signals, plus the per-kernel link byte totals and, if the operation runs beside other streams, their kernel names and durations.
  3. Locate the excess by phase. For each rank, subtract baseline from measured for A (launch path and opening wait), B (count exchange), C (data plane), E (tail and closing wait) and F (hand-off and return). The largest excess names the phase; if the excesses on different ranks differ, the rank with the largest one is the starting point. Phase D is never located directly: it manifests inside C as longer waits.
  4. Apply the attribution rule of that phase (Figure 2). Each rule is a question answered by one signal, and each leaf names an owner.
  5. Confirm by manipulation. The leaf predicts what a knob should change: fewer SMs if the finding is link-side back-pressure (E0), the delayed rank's launch if it is skew (E6), the other stream's traffic if it is a foreign kernel (E8), the block placement if it is a TPC level (E7). One re-run with the knob turned either confirms the owner or sends the diagnosis back to step 3.

5. Where the procedure stops

The red leaf in Figure 2 is reached when the excess sits in C, is uniform over SMs and destinations, and the links carry only this kernel's bytes. The stamps then say "the SM's queue towards the link drained slowly" and nothing more: whether the bytes waited at this GPU's egress port, in the switch, at the peer's ingress or in the peer's memory system is not observable from either end. Two probes remain, both coarse: the SM-count sweep (if throughput follows the per-SM rate the limit is local, if it plateaus the limit is on the path, E0), and a system-scope release once per kernel, which costs a round trip and gives one sample of the path's latency. Everything else requires a signal the hardware does not currently expose: a per-destination completion or arrival counter in the memory system, or port counters with sub-microsecond timestamps readable from the GPU. The diagnosis procedure is therefore also a specification: it says exactly which question that signal would answer and at which leaf it would be consulted.

6. How this differs from FabricPerf's method

  • Signals inside the workload, not in a probe. FabricPerf's T1–T5 are on a synthetic transfer; a production kernel's behaviour under its own contention, scheduling and placement is what degrades, and the probe cannot stand in for it. Cooperative instrumentation through the library costs 1 % and sees every store with its destination.
  • Phases before transfers. Most excess time in the experiments was not in transfers at all: launch allowance, cooperative-launch waits, barriers, host paths, placement. A method that starts at the transfer misattributes all of it.
  • Attribution, not latency. The output is an owner, reached by separating causes that share a signature, rather than a latency distribution. The same slowdown of the data plane had three owners in Figure 3.
  • The observer is accounted for. Clock drift, host mapping error and the perturbation by counter reads are measured and placed; the procedure prescribes where a read may happen.
  • A stated limit. The dark segment is a leaf, not a footnote, and the method says what hardware signal would remove it.
