A model for scale-up communication and its telemetry

What DeepEP taught us about GPU-to-GPU communication by direct memory writes, explained with pictures for readers new to the field.

notes · model, built from experiments E0–E9 on h100x4 · 2026-10-14

This page explains, for a reader who is new to the field, what we learned from DeepEP about communication between GPUs that works by writing directly into another GPU's memory, and how those lessons form a general model. Every idea has a picture. Terms are defined where they first appear.

Words used on this page

  • Scale-up network: the links that connect the GPUs inside one server (NVLink), as opposed to the network between servers.
  • Memory-semantic communication: a GPU moves data by executing a normal store instruction whose address is in another GPU's memory. There is no "send" and no "receive" function.
  • Store: one write instruction. DeepEP uses a bulk store, which writes a block of about 14 KB in one instruction.
  • Flag: a small word (4 or 8 bytes) that one GPU writes after its data, to tell the other GPU "the data is there". The other GPU reads the flag again and again (polls) until it changes.
  • Rank: one GPU taking part in the operation. In our runs there are four ranks.
  • Warp: a group of 32 threads that execute together. SM: a processor inside the GPU; an H100 has 132 of them. Block: the group of warps a kernel places on one SM.
  • Barrier: a point that all ranks must reach before any of them may continue.
  • Telemetry / observability: the signals a system gives out while running, and what can be concluded from them.
  • Stamp: a clock value written by a thread at a chosen point in the code.

1. What kind of communication this is

In message-based communication the hardware moves packets, and every packet is an event that can be counted and timed. In memory-semantic communication the hardware moves bytes written by a store instruction. The receiving GPU does not run any code for it. The only way the receiver learns that the data has arrived is a flag that the sender writes afterwards. This single difference is the root of the observability problem.

2. The four milestones of one store

Measured on this machine (experiment E1): a bulk store reports milestone M2 for free, about 150 to 400 ns after it was issued, and it reports it at the same time whether the data goes to the GPU's own memory or to another GPU. So M2 tells the sender nothing about the other GPU or the link. Milestone M3 can be forced with a release instruction, but it costs a full round trip of about 1.8 µs, so DeepEP uses it once per kernel. Milestone M4 exists only for the words that the receiver polls.

This also explains an important correctness fact: if a sender writes the data, waits for M2, and then writes a flag, the flag can arrive before the data (we saw stale data in 52 of 2,000 trials). The flag must be written with a release, which is what DeepEP's barrier does.

3. How much data does one flag cover?

This is the parameter that decides how finely a problem can be located. We call it coverage: the amount of data between two consecutive flags.

So FabricPerf's method is not wrong. Its five probe points are the milestones of Figure 2 for one message with one flag. DeepEP has the same milestones, but one flag covers eleven thousand stores. The method can be applied to DeepEP, and it then measures the whole operation as one unit, which is what the closing barrier already does. What FabricPerf's method cannot do is look inside the operation, and that is where all the degradations we found were.

4. Who waits for whom

A performance problem is often seen at a different place from where it is caused. This happens whenever one part of the system must wait for another part. There are three such places in DeepEP, and all three exist in any scale-up collective.

Each of these three has a matching rule for finding the real cause. For the barrier: compare the arrival times of all ranks on one clock, and the last one is the cause. For the queue: compare the latency of stores to different destinations; if they are all equally slow, the queue in front of them is full and no single destination is to blame. For the scheduler: compare warps of the same block; a fixed group of them is always faster.

5. The path of one store, and where software can see it

Two of these findings surprised us. First, how much of the time is before and after the kernel: in a small (decode-size) operation the host spends 100 µs around a 43 µs kernel. Second, how much the physical place of a block matters: a block on a slow SM pair finishes 40 % later than a block on a fast pair, every time, and this decides which warp is last. Neither of these is "the network", but both would be reported as communication time by any tool that only measures kernel duration.

6. The phases of an operation, and which of them are optional

Putting the parts together, an operation on a scale-up network consists of moving the data plus up to four kinds of synchronisation information that must reach some party:

  1. Readiness: the sender must know the receiver's buffer is free before writing into it. Needed only when buffers are reused. DeepEP carries it with one global barrier at the start. NCCL carries it with a small "buffer free" flag per chunk. A one-shot operation into a fresh buffer does not need it.
  2. Sizes and shape: the receiver must know how much data it will get and where. Needed only when the sizes are not known in advance. MoE dispatch and variable-size all-to-all need it; all-reduce, all-gather and reduce-scatter do not, because every rank knows the sizes from the call. When it is needed it can come before the data, as in DeepEP's normal mode (so the receiver can allocate), or together with the completion signal, if buffers are pre-allocated at maximum size.
  3. Completion: the receiver must know the data has arrived. Always needed. Carried by a flag whose coverage is the parameter of Section 3.
  4. Hand-off: a host or a following kernel must be told that the result is usable. Needed when the consumer is not the same kernel.

So the earlier phrase "every operation goes through five phases" was too strong. Correct is: every operation moves data and signals completion; readiness, sizes and hand-off are present only when the operation needs them, and each can be carried by a global barrier, by per-chunk flags, or not at all. DeepEP happens to need all four, which is one reason it was a useful case to study, but it is not the rule. The diagnosis procedure is unchanged by this: step 3 locates the excess in whichever of these parts the operation actually has.

7. The model in one paragraph

A scale-up communication operation is a set of memory-semantic instructions, each passing through the milestones issued, accepted, visible, seen. The instructions are grouped by flags; the amount of data between two flags is the coverage. Parts of the system wait for each other through barriers (between ranks), shared queues (between destinations) and shared schedulers (between warps). The data travels along a path of hardware parts, some of which produce events and some of which do not. The operation moves data and must deliver completion; it may also need readiness, sizes and hand-off, each carried globally, per chunk, or not at all. Telemetry for such an operation consists of three kinds of signal: stamps at the milestones that exist, byte counters at the parts of the path that have them, and one clock shared by all ranks so that stamps from different GPUs can be compared. What can be diagnosed follows from the coverage and the waiting relations; what cannot be diagnosed is the part of the path between the sender's queue and the receiver's memory, in any system whose coverage is coarse.

8. A telemetry method built on the model

The model is useful only if it tells us what to measure and how to reason. This section does that. It is written for any scale-up collective, not only DeepEP; the DeepEP numbers are examples.

8.1 Where to put the signals

  1. Stamp the milestones that are free. For each kind of instruction, find which of the four milestones produces an event at no cost (for a bulk store: issued and accepted; for a polled flag: seen). Read the clock there and record who did it (rank, SM, warp, lane), to whom (destination rank), and how much (bytes). The library already knows all of these when it issues the instruction, so this is cheap: about 1 % of kernel time in DeepEP.
  2. Choose the side from the coverage. If the system writes a flag per message, the receiver sees "seen" for each message and is the better side to instrument. If the system writes one flag per operation, the receiver sees nothing useful and the sender is the only side with per-store events. DeepEP is the second case.
  3. Stamp the boundaries of the phases the operation has on one thread per rank: kernel entry, readiness barrier arrive and release (if any), size exchange done (if any), last data store accepted, completion barrier, kernel end; plus two host stamps, before the call and after the return.
  4. Share one clock. Measure the clock offset between every pair of GPUs right before and right after each operation. A one-time calibration is wrong within minutes.
  5. Read counters outside, not inside. The byte counters of the ports are the only signal for the parts of the path without events. Read them before and after the operation. A read during the operation changed the kernel by 20 % in our runs.
  6. Keep a baseline. Run the same configuration quietly and keep the median of every quantity, including the per-SM finish levels of each GPU.

8.2 Buying visibility where the system gives none: the coverage knob

When the flags are coarse, the sender can still create a "visible" milestone itself by executing a release instruction, which waits until all its previous stores are visible on the other GPU. This costs one round trip, so it cannot be done for every store, but it can be done every k stores. This turns coverage into a knob.

8.4 The procedure

  1. Baseline. A quiet run with all stamps on.
  2. Record the slow operation with the same stamps, the clock offsets, and the port bytes before and after.
  3. Locate the phase. For each rank, subtract the baseline from the measured time of each phase the operation has (readiness, sizes, data, completion, hand-off). The largest difference names the phase; the rank with the largest difference is the starting rank.
  4. Apply the test of that phase (Figure 9, middle row). Each test ends at an owner: a peer's preceding work, the launch queue, the host, this operation's own data plane, local memory, block placement, routing, a foreign kernel, or the dark segment.
  5. Confirm by changing one thing. Each owner predicts a knob that should move the excess. If it does not move, the owner was wrong; return to step 3.
  6. If the answer is the dark segment, turn the coverage knob: add one release per warp, re-record, and read the accepted-to-visible time. This says how long the bytes spent on the path, though not where.

8.5 Applying the method to a new system

To use this on a system other than DeepEP, answer four questions about it: which instructions it uses and which milestones they report for free; how much data one flag covers on each side; where its barriers, shared queues and shared schedulers are; and which parts of its path have counters. The answers fill in Figure 7, and the procedure of Figure 9 follows unchanged. For NCCL the answers are known in outline: fixed sizes, so no size exchange; per-chunk flags for both readiness and completion, so instrument the receiver's polls; the same SM queues on the sender; the same ports. The model predicts that NCCL will see arrival delays per chunk and will not see which sender SM was slow, the mirror image of DeepEP.

8.6 What the method cannot do, stated plainly

  • It cannot say where on the path between the sender's queue and the receiver's memory the bytes waited. It can say how long (with the coverage knob) and whether bytes of another kernel were there (with the port counters).
  • It cannot see a slow receiver at all when the flags are per operation. Only the receiver's own polls (if any) or hardware counters at the receiver's port can.
  • Its host-side resolution is about 5 µs, which is as large as some phases of a decode-size operation.
  • Its counters are read from the host and disturb the system. Counters readable from the GPU, or a per-destination "accepted and visible" counter in the memory system, are what the method asks the hardware for.

9. Why DeepEP was a good case, and what to do next

DeepEP sits at one end of the coverage scale: the coarsest possible flags on the receiver side and, because the library knows every store it issues, the finest possible events on the sender side. That made it show clearly which parts of the problem are not about the network at all (host, launch, placement, schedulers) and exactly where the sender's view stops. A system at the other end of the scale, NCCL with its per-chunk flags, should show the opposite: good visibility of arrival on the receiver, little visibility of what each sender SM did. Measuring NCCL on the same GPUs with the same stamps is the next step. If the model predicts correctly what each system can and cannot see, the model is general, and the telemetry proposal that follows from it, a cheap per-destination "accepted and visible" counter in hardware, applies to all of them.
